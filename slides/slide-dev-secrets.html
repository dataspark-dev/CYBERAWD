Where a credential lives is a security decision, not a convenience one.

Hardcoded Keys In Source Risk

An API key or password committed to a repo is compromised the moment it's pushed — even a deleted commit stays in git history forever.

Static Tokens In Frontend Code Risk

Anything shipped to a browser or mobile app is public, no matter how it's obfuscated — a token embedded there is a token anyone can extract.

Vault-Managed Secrets (KMS / HashiCorp Vault) Good Practice

Secrets are fetched at runtime from a managed vault, never checked into source or baked into a build artifact.

Short-Lived, Rotated Tokens Good Practice

A token that expires in minutes or hours limits what a leak can do — long-lived static credentials are a standing liability by design.

Scoped IAM Per Environment Good Practice

Dev, staging, and production each get their own narrowly-scoped credentials — a leaked dev token should never be able to touch production.

This connects directly to this month's activities: the secret-in-a-config-file scenario in Fault Finding is built on exactly this gap — a real key sitting somewhere it should never have been committed.
Starting today: Never commit a secret, even in a private repo Fetch secrets from a vault at runtime, not from source Prefer short-lived, scoped, rotated tokens over static ones
[SECRETS] GOLDEN RULE: Treat every secret as radioactive — it belongs in a vault with a short lifetime and a narrow scope, never in source, a frontend bundle, or an unencrypted .env file.
